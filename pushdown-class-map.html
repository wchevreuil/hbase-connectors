Pushdown module class map

Classes in the shared pushdown module (methods omitted) and every main-code link from the spark (Spark 3) and spark4 connectors. spark4/hbase-spark-pushdown has no sources of its own: its pom adds spark/hbase-spark-pushdown/src/main/{java,scala} through build-helper and recompiles them for Scala 2.13. Both connectors therefore see the same classes.

Arrow legend

A --|> BA extends B
A ..|> BA implements B, or mixes in trait B
A o-- BA holds a reference to B (field)
A *-- BA is composed of B
A --> BA has a field typed B
A ..> BA uses or creates B

Who touches the pushdown classes

hbase-spark-pushdown (shared)

spark/hbase-spark-pushdown/src/main
  • SparkSQLPushDownFilter: the HBase filter that runs on the region server
  • DynamicLogicExpression tree: 11 node types plus the string builder
  • BytesEncoder / JavaBytesEncoder: encoder plug-in and compare ops
  • PushdownMappedField: lets each connector pass its own Field

spark (Spark 3)

spark/hbase-spark
  • HBaseRelation (DefaultSource.scala) turns Spark filters into an expression tree and builds the filter
  • HBaseTableScanRDD carries it; SerializedFilter ships it to executors as bytes
  • NaiveEncoder implements BytesEncoder

spark4

spark4/hbase-spark4
  • HBaseScanBuilder creates the encoder; HBaseScan uses it for row-key ranges
  • HBasePartitionReader builds the expression tree and filter per partition
  • NaiveEncoder implements BytesEncoder

Side finding

JavaBytesEncoder.naiveFallbackEncoder() tries org.apache.hadoop.hbase.spark4.datasources.NaiveEncoder first. That class does not exist: spark4's NaiveEncoder lives in org.apache.hadoop.hbase.spark.datasources, the same package as Spark 3's. The second candidate resolves in both connectors, so the fallback works, but the first entry is dead.
